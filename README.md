# AI-Based Fruit Detection and Freshness Analysis

A complete computer-vision project: a 16-class fruit condition classifier trained from scratch on
the *Fresh and Rotten Fruits* dataset, wrapped in a Flask website that returns real model
predictions for an uploaded photograph.

Upload a photo → the site reports the fruit, whether it looks fresh or rotten, the fresh/rotten
model probabilities, the model's identification confidence, a conservative visual-edibility
statement, explicit warnings when the image is outside the model's validated scope, and an honest
"not available" message for shelf life.

> **This is a visual AI assessment, not a food-safety instrument.** It cannot guarantee that a fruit
> is safe to eat.

---

## 1. What the system does

| Capability | Status |
|-----------|--------|
| Identify one of 8 fruits (Apple, Banana, Orange, Grape, Guava, Jujube, Pomegranate, Strawberry) | ✅ implemented, evaluated |
| Classify condition as fresh/good or rotten/bad | ✅ implemented, evaluated |
| Fresh % and rotten % (summed model probabilities) | ✅ implemented |
| Separate fruit-identification confidence | ✅ implemented |
| Calibrated probabilities (temperature scaling) + ECE reporting | ✅ implemented |
| Unknown / invalid image handling with a documented gate | ✅ implemented, probed |
| Remaining shelf life in days | ❌ **not possible** — the dataset has no time-based labels |
| Validated cross-section (cut fruit) analysis | ❌ **not claimed** — too few, unlabelled examples |
| Certainty that the fruit is safe to eat | ❌ **never claimed** — physically impossible from a photo |

## 2. Results

The model is evaluated **once** on a held-out test split that was never used for training or model
selection (480 images, 30 per class). Numbers are generated by `python -m SRC.models.evaluate` and
stored in `Evaluation/metrics/metrics.json`; the figures below are copied from that run.

| Metric | Result |
|--------|--------|
| Test images (untouched) | **480** — 30 per class |
| 16-class test accuracy | **96.88 %** |
| Macro precision / recall / F1 | **97.16 % / 96.88 % / 96.89 %** |
| Weighted F1 | **96.89 %** |
| Fruit-level accuracy (8-way identify) | **97.50 %** |
| **Condition accuracy (fresh vs rotten)** | **98.75 %** |
| Best validation accuracy (checkpoint chosen) | 97.50 % — stage B fine-tuned model |
| Inference time (CPU, batch 1) | 83.5 ms mean / 65.5 ms median per image |
| Throughput (CPU, batch 32) | 92.1 images/s |
| Calibration | T = 1.077 fitted on validation; test ECE 1.45 % → 1.65 %, NLL 0.0848 → 0.0851 |
| Serving gate (identity) | declines to name a fruit for **4.58 %** of test images (validation target ≤ 2 %, achieved 1.87 %) |
| Serving gate (unknown input) | rejects **71.7 %** of 120 synthetic non-fruit probes, 40 % of flat colour images, 80 % of very dark photographs |
| Rotten pomegranate | 28/30 correct, precision 1.000, recall 0.933; 2/30 declined by the gate |
| Architecture check | multi-task 8 + 2 heads measured **worse** overall (96.46 % vs 96.88 %); 16-class head retained |

Detailed artefacts: `Evaluation/metrics/classification_report.txt`,
`Evaluation/metrics/confusion_matrix.csv`, `Evaluation/confusion_matrices/confusion_matrix.png`,
`Evaluation/figures/training_accuracy.png`, `Evaluation/figures/training_loss.png`,
`Evaluation/figures/calibration_*.png`, `Evaluation/test_results/predictions.csv`,
`Evaluation/test_results/ood_probe.json`.

### How to read these numbers honestly

- **480 test images** means roughly ±2–4 percentage points of uncertainty on accuracy; per-class
  metrics rest on only 30 images each.
- The photographs are studio-style shots of one or a few fruits on plain backgrounds. Phone photos
  with clutter, unusual lighting, occlusion or multiple objects will be less reliable.
- **Condition accuracy is the metric that matters for the website**, because the fresh/rotten score
  aggregates eight classes per condition rather than committing to one exact class.
- Freshness percentages are **model probabilities**, not the physical proportion of the fruit that
  is fresh or rotten, and they are not a measurement of microbial spoilage.

## 3. Data

Source: *Fresh and Rotten Fruits Dataset for Machine-Based Evaluation of Fruit Quality*
(Mendeley Data, DOI [10.17632/bdd69gyhv8.1](https://doi.org/10.17632/bdd69gyhv8.1), CC BY 4.0).

- 3,200 original images, 16 classes, exactly 200 per class, all readable, no corrupted files.
- 7 exact duplicate groups (all inside `FreshOrange`) and 104 near-duplicate groups detected by
  SHA-256 + perceptual hash; **no duplicate group straddles two splits**.
- Split: **2,240 train / 480 validation / 480 test**, stratified per class (140/30/30).
- Augmentation is generated on the fly **from the training split only**.
- The pre-augmented Mendeley archive was deliberately **not** used.

Full details, including the cross-section and shelf-life investigations:
[`Admin/DATASET_DOCUMENTATION.md`](Admin/DATASET_DOCUMENTATION.md).

## 4. Model

- **MobileNetV2** (ImageNet weights) at 224×224, frozen backbone + 256-unit head, then the top 40
  layers fine-tuned with BatchNorm frozen.
- `preprocess_input` is **inside the saved model**, so training and serving preprocessing cannot
  drift; the cached training arrays are produced by the same function inference uses (a test asserts
  byte equality).
- Single 16-class softmax. Fresh score = Σ p(8 fresh classes); rotten score = Σ p(8 rotten classes);
  fruit confidence = Σ p(the two classes of that fruit).
- A small from-scratch CNN is available as a baseline comparison (`--model baseline`).
- Training: early stopping on validation accuracy, best-checkpoint restore, ReduceLROnPlateau,
  CSV logs in `Models/checkpoints/`.

### Two-part gate

Identity and condition are decided separately, because they can differ in confidence and because
fusing them produced contradictory pages (see `Admin/FINAL_FIX_REGISTER.md`, F-01).

| Decision | Threshold | Fitted on | On a low score |
| --- | --- | --- | --- |
| Fruit identity | fruit confidence ≥ 0.75 and fruit margin ≥ 0.30 | validation split | “Unable to identify this fruit confidently…” and no condition is shown |
| Condition | max(fresh, rotten) ≥ 0.673 | validation split | fruit stays identified, condition is marked **uncertain** |
| Capture quality | blur / brightness / resolution | validation split | **advice only** — never rejects a prediction |

Thresholds come from `python -m SRC.models.calibrate_gate` (validation only) and are stored in
`Models/gate_config.json`; the test split is used once, to report. A soft-focus photograph of a
banana the model recognises at 100 % is therefore *warned about*, not thrown away — the first
release discarded 47 correct predictions for exactly that reason.

The measured behaviour on synthetic non-fruit probes, blurred, dark and down-sampled photographs is
in `Evaluation/test_results/{gate_probe,gate_calibration}.json`. **Unseen fruit species remain the
hardest case** and are not reliably rejected — such images are reported with the closest supported
fruit, the gate status and an explicit confidence.

## 6. Setup

### Environment

Tested with **Python 3.12**, Windows 11, TensorFlow 2.20 **CPU**.

Windows notes: TensorFlow has no Python 3.14 wheels, and since TF 2.11 there is **no native Windows
GPU support** (GPU builds are Linux/WSL2 only). The project therefore uses a dedicated 3.12
environment. If you want GPU training, run the same code inside WSL2 with the NVIDIA driver's CUDA
support installed and `tensorflow[and-cuda]` — no code changes are needed.

```bash
# create the environment (uv downloads a standalone Python 3.12; admin rights not required)
python -m pip install --user uv
uv venv .venv --python 3.12
uv pip install --python .venv/Scripts/python.exe -r requirements.txt
```

Or with an existing 3.10–3.12 interpreter:

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows
pip install -r requirements.txt
```

### Pipeline

```bash
# 1. inspect the raw dataset (write the report artefacts)
python -m SRC.data.inspect_dataset
python -m SRC.data.review_sheets --mode full

# 2. build manifest + split, then cache 224x224 arrays
python -m SRC.data.prepare_dataset
python -m SRC.data.prepare_dataset --stage cache

# 3. train (background-safe, logs to Models/train.log)
python -m SRC.models.train --model mobilenet

# 4. fit the serving gate on the VALIDATION split only -> Models/gate_config.json
python -m SRC.models.calibrate_gate

# 5. evaluate on the untouched test split (reports the gate, never tunes it)
python -m SRC.models.evaluate

# 6. per-fruit error analysis and full serving-gate measurement
python -m SRC.models.per_fruit_report
python -m SRC.models.gate_report

# 7. run the website
python -m Website.app --port 5000     # http://127.0.0.1:5000
```

Optional comparison runs: `--model baseline` (from-scratch CNN) and
`python -m SRC.models.train_multitask` (8 + 2 heads instead of one 16-class head).

Every stage is resumable: `prepare_dataset --stage {manifest,cache,metadata}`.

## 8. Deploying to Render

The repository ships a [Render Blueprint](render.yaml), so deployment is one step: push the code,
then **Render Dashboard → New → Blueprint → select this repository**. Render reads `render.yaml` and
creates a single free web service with the right commands, health check and environment variables.
No secrets or API keys are required — the trained model is committed.

| Setting | Value |
|---------|-------|
| Runtime | Python 3.12 (`.python-version`) |
| Build | `pip install --upgrade pip && pip install -r requirements.txt` |
| Start | `gunicorn --bind 0.0.0.0:$PORT --worker-class gthread --workers 1 --threads 4 --timeout 180 Website.app:app` |
| Health check | `/healthz` (instant) · `/api/health` (model warmed) |
| Model file | `Models/final_model/fruit_model.keras` (27 MB, under GitHub's 100 MB limit) |

**Manual alternative:** create a *Web Service*, connect the repository, and paste the build and start
commands above. Nothing else needs configuring.

### What the free tier changes — read this before demoing

1. **512 MB RAM, one worker.** TensorFlow plus MobileNetV2 needs roughly 350–450 MB, so the start
   command deliberately uses **one worker with four threads** instead of two worker processes. Two
   workers would hold two copies of the model and be killed for exceeding memory.
2. **Sleeps after ~15 minutes idle.** The first request afterwards takes **30–60 seconds** while the
   container boots and TensorFlow imports. Open the URL yourself a minute before any demo.
3. **Ephemeral disk.** Uploaded photographs live in `Website/static/uploads/` and disappear on
   restart or redeploy. Nothing else is written at runtime; results are computed per request.
4. **CPU inference only.** Measured 83.5 ms per image locally on CPU; expect a similar order of
   magnitude on a free instance, plus queueing when several people upload at once.

### Configuration and secrets

**The app needs no API keys and no secrets.** Everything tunable is an environment variable with a
working default, read in [`Website/config.py`](Website/config.py) — nothing is hardcoded in the
request path. Set them in the Render dashboard (*Environment*), in Docker, or in a local `.env`
(copied from [`.env.example`](.env.example), git-ignored; real environment variables always win).

| Variable | Default | Effect |
|---|---|---|
| `HOST` / `PORT` | `127.0.0.1` / `5000` | Bind address for `python -m Website.app`; Render injects `PORT`, and gunicorn reads it directly |
| `LOG_LEVEL` | `INFO` | Flask logger level |
| `FLASK_DEBUG` | off | Flask debug reloader — never enable in production |
| `MODELS_DIR` | `Models` | Where the trained artefacts live (volume, release folder, read-only image) |
| `METRICS_PATH` | `Evaluation/metrics/metrics.json` | Model-card numbers served by `/api/model-info` |
| `UPLOAD_DIR` | `Website/static/uploads` | Where accepted photographs are written |
| `MAX_UPLOAD_MB` | `8` | Rejected above this with HTTP 413 |
| `MAX_IMAGE_PIXELS` | `40000000` | Decompression-bomb guard |
| `MIN_IMAGE_SIDE` | `64` | Smallest accepted side, in pixels |
| `UPLOAD_TTL_SECONDS` | `3600` | Age at which stored uploads are pruned |
| `SECRET_KEY` | unset | Optional Flask session secret; only needed if sessions are added later |

The blueprint also sets `PYTHON_VERSION`, `TF_CPP_MIN_LOG_LEVEL`, `TF_NUM_INTRAOP_THREADS`,
`TF_NUM_INTEROP_THREADS`, `OMP_NUM_THREADS` and `MALLOC_ARENA_MAX`, which keep TensorFlow quiet and
stop its thread pools from multiplying memory use.

To rehearse the production server locally (Linux/macOS, or WSL):

```bash
gunicorn --bind 127.0.0.1:8000 --worker-class gthread --workers 1 --threads 4 Website.app:app
```

## 9. Website API

| Endpoint | Purpose |
|----------|---------|
| `GET /` | single-page UI |
| `POST /api/analyze` | multipart `image` → full analysis JSON |
| `GET /api/model-info` | model card numbers from the evaluation run |
| `GET /api/health` | readiness / model availability |
| `DELETE /api/uploads/<name>` | clear/reset: delete one stored upload |

Uploads are limited to 8 MB and 40 MP, checked by extension, Pillow `verify()` and pixel count,
stored under `Website/static/uploads/` with sanitised names, and never executed. Stale uploads are
removed after one hour.

## 10. Honest limitations

1. **No shelf life.** The dataset has only fresh/rotten labels; there is no storage age, temperature
   or spoilage timeline. The API returns `available: false` with the reason rather than guessing.
2. **No validated cross-section support.** A small, unlabelled fraction of the data shows cut fruit;
   the model is validated for whole-fruit photographs. The pipeline has a documented extension hook
   (`image_type` / `cross_section_validated`) for future labelled data.
3. **Probabilities are estimates.** Temperature scaling improves calibration on this dataset, but
   reported percentages remain model estimates, not physical measurements.
4. **Out-of-vocabulary fruits.** A mango or a dragon fruit is not one of the eight classes; the gate
   reduces but cannot eliminate confident mistakes. Low confidence is surfaced, not hidden.
5. **Domain shift and dataset size.** 3,200 studio-style images across 16 classes is small; expect
   lower accuracy on real-world phone photos.
6. **Visual freshness ≠ food safety.** Always shown with the mandatory disclaimer.
